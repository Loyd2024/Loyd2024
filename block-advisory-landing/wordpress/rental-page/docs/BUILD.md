## 1. Two layers, built at different times

The page's look is still being chosen (three concepts under `ROOT/design/concept-a|b|c/`, a judged final design will
land in `ROOT/design/final/`). So the snippet is built in two layers:

- **The engine** (now): everything that does not depend on the look. Which request gets the page; standing the
  development snippet down; reading a listing into one plain array (the *model*); reading the description; the
  enquiry endpoint, storage, email and CRM hand-off; the admin controls; previews. The engine ships with a
  **plain skin** (unstyled, semantic HTML of everything in the model, a working form, a few lines of script) so that
  it can be tested end to end before the design is final.
- **The skin** (when the design is final): the templates, the stylesheet and the script that draw the model as the
  final design, replacing the plain skin. The skin reads only the model and calls only the engine's documented
  helpers.

The model must therefore carry the union of what any of the three concepts needs. Read each concept's `spec.md`
sections on components, data needs, states and "how the page reads a listing", and each concept's `build.py`
(three independent prototypes, in Python, of reading a real listing; they disagree in places, which is useful).

```
    50-leads.php          the enquiry endpoint, the no-script form, storage, email, CRM

    70-skin.php           templates (plain skin now; the final design later)
    80-css.php            generated by build.py from skin/bkr.css

    99-foot.php           closes the guard
  skin/bkr.css, skin/bkr.js
  build/build.py          joins src/ into REPO/block-rental-page.php (with the opening PHP tag, as the other snippets in
                          the repo) and RP/dist/block-rental-page-paste-into-WPCode.txt (no opening tag), and runs the
                          source checks of section 5
  tests/                  everything that proves it works (section 6)
  docs/ARCHITECTURE.md    the contract the architect writes; everybody builds to it
  docs/, notes/           copies of the brief, decisions and mapping notes (already there)
```

Each `src/NN-*.php` file starts with an opening PHP tag and a one-line comment and holds only function
definitions and hook registrations that belong inside the guard; `build.py` strips the opening tags and indents
nothing. No file may depend on being a separate file (`__FILE__`, `__DIR__`, `require`): the snippet is `eval`ed by
WPCode.

## 4. What the architect must fix in `docs/ARCHITECTURE.md` before anyone codes

1. **Names**: every function with its signature, return shape, the module that owns it, and whether the skin may
   call it. Prefix `blockke_rp_`. Config: `blockke_rp_config()` (defaults merged with the option
   `blockke_rent_page`), with every key, its type, default and meaning: at least `enabled`, `auto`, `preview_key`,
   `trust_line`, `notify_emails` (empty = use the development snippet's or the popup's list, else the site admin),
   `count_views`, `zoho` (on/off), `similar_count`. Filters the site owner could use later: keep to a handful.
2. **The request lifecycle**: every hook, its priority and why (notes/01 "Recommendations" 1 and 5; notes/04; notes/05
   section 12), including what is printed where: styles in the head, the `#bkr` root between `get_header()` and
   `get_footer()`, the phone bar, dialogs and the script at `wp_footer`. Styles are printed with WordPress's style
   API (`wp_register_style( 'bkr', false )`, `wp_add_inline_style`), the script and any JSON-LD with
   `wp_print_inline_script_tag()`: the source never contains a hand-written script or style tag (PROJECT.md rule 5).
3. **The switch** as a truth table: option unset, `enabled`, `auto`, `bke_rent_layout` (`''`, `on`, `off`), editor
   with `?bkr=1` or `?bkr=0`, `?bkr_key=`, a listing that is not a rental, a rental whose title also offers a sale,
   let or sold status, password-protected or unpublished listings, feeds, embeds, the admin, REST, page-builder
   previews, `?print`. Which responses are `noindex` and uncached.
4. **The model**: one array for a listing, every key with type, source field or parse rule, and the DECISIONS number
   it implements. It must cover at least: ids, URL, the cleaned title (H1), building name, kind (`home` or
   `commercial`), state (`available`, `let`), area, city and their links, breadcrumb, the rent (amount, currency,
   period, "From", on request, the sentence, the short form for the bar, the USD note), what the rent includes, the
   stated terms (service charge, deposit, lease, availability, furnishing; each only when DECISIONS 10 to 13 allow)
   and the "to confirm" list (DECISIONS 14) for homes and for commercial, facts (bedrooms, bathrooms, size in both
   units for homes, sq ft for commercial), features without group terms (notes/08), photos (id, URLs for the sizes
   the skin needs, width, height, alt; the order rule), the agent (name, role, portrait, phone, display phone,
   WhatsApp number) with Block's default, every WhatsApp message (general, per question, with the "please also
   confirm" items) and the Ref code, the location (area, address when present, map link built from the pin, nearby
   places as the listing's text states them), the description as ordered sections (see 5) plus the designed
   extracts (amenities, who it suits, location, FAQ, the listing's own terms text, the closing "arrange a viewing"
   section flagged so a skin can leave it out), "more to rent in this building", similar rentals (cards: title,
   URL, rent sentence, facts, photo), the "all rentals in the area" link (DECISIONS 19), the generic copy for
   homes and commercial as keyed strings, the form's fields and endpoint details, and the data the script needs.
   Cached how, and invalidated when (the listing is saved, a term changes, the snippet's version changes).
5. **The description reader**: input (stored `post_content`, never through `the_content` filters), cleaning
   (DECISIONS 16) done with WordPress's HTML API rather than tag-matching regexes, sections at any heading level
   and bold-only paragraphs as headings (DECISIONS 9), tables as rows of label and value, lists, the FAQ (plain
   headings and the Rank Math FAQ block), the classification of a section (overview, snapshot or "at a glance"
   table, rent and terms, amenities, location, who it suits, FAQ, contact or arrange-a-viewing, market or
   investment text to leave out, other) with the heading patterns found in `ROOT/notes/03-data-audit.md`, the
   rules for each stated term (DECISIONS 10 to 13 with the misreads D1 to D10 of `ROOT/notes/02-rental-rules.md`
   section 19), and the fallback when nothing is recognised: the description as written, whole and safe
   (`wp_kses_post`).
6. **Enquiries**: the route `block/v1/rental-lead` (fields, validation, limits, the honeypot's name, the rate
   limit and how the visitor's address is read, responses and their texts), the order of work (save first, then
   email, then CRM; nothing a visitor waits for may take more than a moment: say how the slow steps are kept off
   the response), the saved row (exactly the development snippet's format with `'kind' => 'rent'`,
   `ROOT/notes/01-dev-layout.md` section (f) and `ROOT/notes/02-rental-rules.md` section 13), the email (subject
   "[Block] Rental enquiry: {name} - {listing}", recipients, a safe Reply-To), the CRM call
   (`ROOT/notes/05-live-snippets.md` sections 2 and 12: all fifteen keys, "Individual tenant", behind
   `function_exists`), the follow-up or correction of a sent enquiry (one row, by its reference), the form without
   JavaScript (posts to the listing's own URL and comes back with a thank-you or the errors, own parameter names),
   the "similar homes" enquiry of a let listing, and the attribution the script sends (`blkbp_attr`).
7. **Admin**: a settings screen (Tools, "Rental page"; `manage_options`; nonce; every value sanitised) with:
   status (off; preview only; live for all rentals; live only for listings switched on one by one), the optional
   trust line, the notify list, a preview link the owner can share (creates or resets `preview_key`), and a short
   list of what the automatic rule currently accepts and rejects with reasons. A box on the listing's edit screen
   ("Rental page": Automatic, On, Off, with a preview link and the reason the automatic rule gives), saved the way
   the development snippet saves its box (`ROOT/notes/01-dev-layout.md` section (i)). Admin-bar links on a rental
   for editors (the node id `bkr` is taken by v1.9.1: use `bkr-page`). No other admin surface.
8. **The skin interface**: the functions the skin provides (`blockke_rp_render( $m )` for the `#bkr` root,
   `blockke_rp_render_foot( $m )` for what is printed at `wp_footer`, `blockke_rp_css()`, `blockke_rp_js()`), the
   settings object `window.BKR` (keys), the form's field names, the events the script must fire on a sent enquiry
   (`ROOT/notes/05-live-snippets.md` section 12: `generate_lead`, `window.blockkeLeadConversion('lead_form')`,
   `fbq` Lead), and `data-blkct="1"` on every WhatsApp link.
9. **Tests** (section 6): the list of test files, what each asserts, and the fixtures used.

The architect also writes the skeleton so the owners can start at once: `00-head.php`, `10-util.php` (ported
helpers), `99-foot.php`, empty-but-loading `20` to `60` files with the agreed function names as stubs that return

## 5. Source rules that `build.py` checks on every build (fail the build when broken)

- PHP: `php -l` passes; no `declare(strict_types)`; no typed properties, union types, `match`, enums, named
  arguments, nullsafe `?->`, `readonly`, first-class callable syntax, `never`, trailing comma in parameter lists,
  arrow functions are allowed (7.4), `static fn` allowed; `array()` or `[]` both fine; no implicit nullable
  parameters (`Type $x = null`); no dynamic properties; no `create_function`, `each`, `utf8_encode`,
  `strftime`. (PHP 7.4 to 8.5, PROJECT.md rule 2.) If `composer` can fetch PHPCompatibility, run it as well.
- No backslash directly followed by `u` and four hex digits anywhere in the built file (PHP, CSS or JS).
- No hand-written script or style tag text, and no regex written to match those tags; no `eval`, `base64_decode`,
  `create_function`, `assert(` with a string, `extract(`, `$$`, backticks, `shell_exec`, `file_put_contents`.
- Never encode, split or disguise text to get it past a filter. If something cannot be written plainly, leave it
  out and note it in `docs/REQUESTS.md`.
- Only the names of PROJECT.md rule 1 for new things; none of the names to avoid (DECISIONS 30;
  `ROOT/notes/01-dev-layout.md` "What to avoid").
- The file starts with the same two marker comment lines as `REPO/block-enquiries-inbox.php` (after the opening
  tag), uses tabs, Unix newlines, UTF-8 without BOM, and ends with a newline.
- Sizes are printed: the built file, the CSS and the JS (budgets: CSS about 35 KB, JS about 18 KB).

## 6. Tests

All tests run against the local test site (`ROOT/rig/README.md`, `ROOT/rig/FIXTURES.md`), never against block.ke.

- **Never enable a snippet on the main rig (port 8089)**: designers and judges are using it. Make your own clone:
  `ROOT/rig/bin/clone <your key> <port>` (ports: engine-architect 8110, engine-parse 8111, engine-model 8112,
  engine-switch 8113, engine-leads 8114, engine-integrator 8115, oracle 8116; testers 8120 and up), enable
  snippets and change options only there, and remove the clone when you finish unless told to keep it.
- Unit tests are PHP files run with `<clone>/bin/wp-eval`; browser tests are Playwright scripts that reuse
  `ROOT/rig/bin/shot.js`. A test prints one line per assertion that fails and ends with a count; exit code 1 on any
  failure.
- **The oracle**: `RP/tests/expected/fixtures.json` (written by a separate agent who reads each fixture's page by
  eye and applies DECISIONS by hand) is the ground truth for the model: the rent sentence, the stated terms, the
  "to confirm" list, kind, title, building, facts, features, photo count, FAQ count. When the code and the oracle
  disagree, do not change either to match: write the case into `RP/tests/expected/DISPUTES.md` with the listing's
  own words, and the integrator decides.
- Every fixture, every synthetic state and then all 129 rentals must render with nothing in `debug.log`, in
  `require` mode and in `eval` mode, with the development snippet absent, with v1.8.2 and with v1.9.1.
